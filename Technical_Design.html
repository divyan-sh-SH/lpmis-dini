New — Three Feature Pillars
Habit Tracker
User-defined habits tracked daily. Boolean (done/not) or quantifiable (e.g. 8 glasses). Stored in two tables: definition + daily log.
Unified Calendar
Scrollable date cards combining scheduled events, habit status, and to-dos — no grid. AI reads notes and suggests calendar entries.
To-Do List
Discrete tasks with title, optional due date, and priority. Full CRUD. Appear inside calendar cards on their due date.
⚡

Design Principle — Extend, Don't Break

All three features follow the same patterns already in the codebase: dual-scope (user vs group), UUID primary keys, mutual-exclusivity CHECK constraints, client-side TTL cache with prefix invalidation, and LangGraph embedded protocol blocks for AI action cards. No existing code is deleted — only extended.

Database Design

Four new Supabase (PostgreSQL) tables — all following the existing mutual-exclusivity pattern
💡

Two-Table Pattern for Habits

Habit tracking uses two tables: one for the habit definition (what the user wants to track — configured once) and one for the daily log (did they complete it today). This is the standard approach. A single JSON column would make streak queries and history filtering very difficult.

Habit Log — UPSERT Design
🔑

Why UPSERT?

A user tapping a habit checkbox should work whether they've logged today or not. POST /habit-logs/upsert uses PostgreSQL INSERT ... ON CONFLICT (habit_id, date) DO UPDATE SET ... — the client makes one call, always correct, no pre-check needed.

Calendar Card Design Principles

Cards are grouped by date with a date header. Today's card is highlighted. Within a date, sections appear in order: Events → Habits → Todos. Habits are shown as a 2-column mini-grid with checkboxes. Todos show priority chips. Events show time + title. All-day events come first. The view is purely vertical scroll — no grid, no month view.

✅

Habit Card Design

Boolean habits: one tap on the circle marks done. Quantifiable habits: +/− buttons update the value; a progress bar shows current vs target. Streak count is shown inline as text (e.g. "🔥 12 days") — computed client-side from the log range response. No icon picker, no color picker — name and type are sufficient.

New Intents — agent/state.py
IntentTriggered When
HABIT_QUERY"How's my streak?", "Did I exercise this week?"
HABIT_LOG"Log 7 glasses of water", "Mark meditation done"
TODO_ADD"Add a todo to call the bank"
TODO_QUERY"What's on my to-do list?", "Any overdue tasks?"
CALENDAR_ADD"Schedule a meeting on Friday", or AI detects task in notes
EXTRACT_TODOSAI reads notes and surfaces tasks as todo/calendar suggestions
Graph Node Changes — agent/nodes.py
NodeChange
classify_intentAdd rules for scheduling language, TODO extraction, habit queries. Add habit, todo, calendar as valid entities.
fetch_dataBranch on entity: habit → fetch habits + logs; todo → fetch todos; calendar → fetch notes + upcoming events (to avoid duplicates)
generate_responseSystem prompt extended with CALENDAR_PROTOCOL and TODO_PROTOCOL — LLM embeds suggestion JSON blocks
build_action_cardsParse CALENDAR_SUGGESTIONS: and TODO_SUGGESTIONS: blocks alongside existing ACTION_SUGGESTIONS:
CALENDAR_PROTOCOL — embedded in agent/prompts/generate.py
"""
CALENDAR_PROTOCOL:
When you detect TODO items, tasks, or scheduling intent in the user's notes or message:
1. Identify the task and estimate a date/time from note content and today's date.
2. Embed a calendar suggestion block in your response:

CALENDAR_SUGGESTIONS:
[
  {
    "type": "add",
    "entity": "calendar",
    "label": "Schedule: Buy groceries",
    "data": {
      "title": "Buy groceries",
      "description": "From note: need to pick up vegetables and dairy",
      "date": "2026-09-01",
      "time_start": "10:00",
      "time_end": "11:00"
    }
  }
]

Rules:
- Infer date from urgency cues ("tomorrow", "this weekend", "before Friday")
- Default to a morning slot (09:00–10:00) if no time is mentioned
- Never suggest an event that already appears in the provided calendar context
"""

# Same pattern as the existing ACTION_SUGGESTIONS and CART_SUGGESTIONS —
# build_action_cards already parses embedded JSON blocks from the response text.
💡

Why No Graph Rewiring Is Needed

The agent already uses embedded protocol blocks for ACTION_SUGGESTIONS and CART_SUGGESTIONS. Calendar and todo suggestions follow the exact same pattern — just new block labels that build_action_cards learns to parse. The LangGraph graph structure itself is unchanged; only fetch_data, generate_response, and build_action_cards get new branches.

Data Flow

End-to-end flows — manual creation and AI-assisted scheduling
Manual Calendar Event / Todo / Habit Log

User taps action button

"+ Add Event", "+ Add Todo", or habit check-in tap

Modal / inline UI

User fills form fields and saves

API call via moneyApi wrapper

POST /homedash/calendar · POST /homedash/todos · POST /homedash/habit-logs/upsert

Cache invalidated

apiCache.invalidate("calendar") / "todos" / "habit-logs" → component re-fetches

AI-Assisted Calendar Entry (Notes → Events)

User asks HomieAgent about notes or tasks

"What's on my list this week?"

classify_intent → EXTRACT_TODOS / CALENDAR_ADD

Entity: calendar. Context: personal or group.

fetch_data

Notes (last 15 days) + upcoming calendar events (next 30 days) — prevents duplicate suggestions

generate_response with CALENDAR_PROTOCOL

LLM embeds CALENDAR_SUGGESTIONS: JSON with inferred dates + times from note content

build_action_cards parses blocks

Returns action_suggestions with entity: "calendar", injects user_id / group_id

Frontend renders action cards

User taps "Add Event" on a suggestion card

HomieAgent dispatches POST /homedash/calendar

Same CRUD call as manual creation — cache invalidated, calendar view updates

🧩

Calendar View: Client-Side Data Merge

On mount, CalendarView fires 3 parallel calls via Promise.allSettled: getCalendarEvents, getUserHabits + getHabitLogs(range), and getTodos. Each resolves independently — a failed call doesn't block the others. The client merges results into a Map<date, {events, habits, todos}> and renders the card list. No backend aggregation endpoint is needed.

Implementation Phases

Build order — each phase independently testable and deployable
🗄️

Phase 1 — Database

Create all 4 tables in Supabase. Add SQLAlchemy ORM models and Pydantic schemas. Verify migrations.

🐍

Phase 2 — Backend

Build all 4 routers. Add UPSERT for habit logs. Register in __init__.py. Test all endpoints directly.

⚛️

Phase 3 — Frontend

Types → API wrappers → HabitFormModal → HabitCheckInGrid → TodoList → CalendarView → header buttons in existing pages.

🤖

Phase 4 — AI

Extend agent state, intents, fetch_data, prompts, and build_action_cards. Update HomieAgent.tsx to dispatch new action card types.

✅

Phase 1–2 carry zero frontend risk

The database migration and new API routes can be deployed to Vercel without any user-facing changes. Phase 3 adds UI against a live, tested API. Phase 4 enhances an already-working feature — the agent degrades gracefully if habit/todo context is empty.
